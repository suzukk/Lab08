## 2. Лабораторийн ажлын зорилго

Энэхүү лабораторийн ажлын зорилго нь JUnit 5 болон Mockito ашиглан программын нэгжийн тест (Unit Test) бичиж сурах юм.

Mockito ашиглан хамааралтай классуудын mock объект үүсгэж, `CourseRegistrationService` классын үйл ажиллагааг бусад системээс тусгаарлан шалгасан. Мөн амжилттай бүртгэл, алдаатай оролт, exception боловсруулах, функцийн дуудлагыг шалгах болон mutation testing хийж, тестүүдийн үр нөлөөг үнэлсэн.

## 4. Тестлэх программын тухай

`CourseRegistrationService` класс нь оюутныг хичээлд бүртгэх үйл ажиллагааг хариуцна.

Уг класс нь дараах хоёр хамааралтай:

- **StudentRepository:** Оюутны мэдээлэл авах, хичээл байгаа эсэх болон урьдчилсан нөхцөлийг шалгах, бүртгэл хадгалах.
- **EmailSender:** Бүртгэл амжилттай болсны дараа баталгаажуулах имэйл илгээх.

Эдгээр классыг Mockito ашиглан mock объект болгон үүсгэсэн. Ингэснээр бодит өгөгдлийн сан болон имэйл сервер ашиглахгүйгээр `CourseRegistrationService` классын үйл ажиллагааг шалгах боломжтой болсон.

|---|---|---|

Ингэснээр нийт **10 тестийн гүйцэтгэл** гарсан.

## 6. Ашигласан Mockito функцүүд

- `mock()` — Хамааралтай классуудын mock объект үүсгэнэ.
- `when().thenReturn()` — Mock методын буцаах утгыг тохируулна.
- `verify()` — Метод дуудагдсан эсэхийг шалгана.
- `never()` — Тухайн метод огт дуудагдаагүй эсэхийг шалгана.
- `verifyNoInteractions()` — Mock объекттой ямар ч харилцан үйлчлэл хийгдээгүйг шалгана.
- `doThrow()` — Имэйл илгээх үед алдаа үүсэх нөхцөлийг дуурайлгана.
- `ArgumentCaptor` — Имэйлийн агуулгыг барьж авч шалгана.
- `@ParameterizedTest` болон `@CsvSource` — Олон нөхцөлийг нэг тестийн методоор шалгана.

### Lenient тохиргоо ашигласан шалтгаан

A8 параметрчилсэн тестэд `lenient()` тохиргоог ашигласан. Учир нь параметр бүр өөр өөр нөхцөлийг шалгадаг тул зарим тохируулсан mock хариу тухайн тестийн гүйцэтгэлд ашиглагдахгүй байж болно. `lenient()` нь ашиглагдаагүй stub-ээс шалтгаалсан unnecessary stubbing алдаанаас сэргийлэхэд тусалдаг.

Гэхдээ `lenient()` тохиргоог шаардлагагүйгээр бүх тестэд хэрэглэхээс зайлсхийх хэрэгтэй.

## 7. Тест ажиллуулсан үр дүн

Тестийг Maven ашиглан ажиллуулсан.

```bash
mvn test 2>&1 | tee results/mvn-test.txt
```

Эцсийн үр дүн:

```text
Tests run: 10, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

Үр дүнгээс харахад 10 тест бүгд амжилттай ажиллаж, алдаа болон бүтэлгүйтсэн тест гараагүй.

## 8. Mutation testing

Mutation testing нь программын кодод зориудаар жижиг өөрчлөлт оруулж, тестүүд тухайн алдааг илрүүлж чадаж байгаа эсэхийг шалгах арга юм.

Энэ лабораторийн ажлаар гурван өөр mutation туршилт хийсэн.

| № | Кодод хийсэн өөрчлөлт | Хүлээгдэж буй үр дүн | Үр дүнгийн файл |
|---|---|---|---|
| 1 | Идэвхгүй оюутны шалгалтыг арилгасан | Тестүүд бүтэлгүйтэж `BUILD FAILURE` гарах | `results/mvn-test-mutant-1.txt` |
| 2 | Бүртгэл хадгалах методын дуудлагыг арилгасан | Тестүүд бүтэлгүйтэж `BUILD FAILURE` гарах | `results/mvn-test-mutant-2.txt` |
| 3 | `null` шалгалтаас хичээлийн кодын нөхцөлийг хассан | A6 тест бүтэлгүйтэж `BUILD FAILURE` гарах | `results/mvn-test-mutant-3.txt` |

Гурван туршилтын үед тестүүд алдааг илрүүлж, `BUILD FAILURE` үр дүн гарсан. Дараа нь өөрчилсөн кодыг анхны хувилбарт нь сэргээж, тестийг дахин ажиллуулахад 10 тест бүгд амжилттай болсон.

## 9. Mock болон Fake объектын ялгаа

**Mock объект** нь хамааралтай классын үйлдлийг дуурайлган, ямар метод дуудагдсан болон ямар аргумент дамжуулсныг шалгахад ашиглагддаг. Mockito-ийн `verify()` болон `when()` функцүүд нь mock объекттой ажиллах боломж олгодог.

**Fake объект** нь бодит компонентыг хялбаршуулсан байдлаар орлож, тодорхой хэмжээний бодит үйл ажиллагаа гүйцэтгэдэг. Жишээлбэл, өгөгдлийн сангийн оронд мэдээллийг санах ойд хадгалдаг энгийн repository байж болно.

Mock нь харилцан үйлчлэлийг шалгахад тохиромжтой бол fake нь бодит үйл ажиллагаатай төстэй логикийг шалгахад тохиромжтой.

## 10. Хэт их verify ашиглахын эрсдэл

`verify()`-г шаардлагагүй олон ашиглах нь тестийг программын дотоод хэрэгжилтээс хэт хамааралтай болгож болно. Үүний улмаас программын үр дүн өөрчлөгдөөгүй байсан ч кодын бүтцийг өөрчлөхөд тест бүтэлгүйтэх эрсдэлтэй.

Тиймээс зөвхөн шаардлагатай харилцан үйлчлэлийг шалгаж, тестийг ойлгомжтой, засварлахад хялбар байлгах нь чухал.

## 11. Дүгнэлт

Энэхүү лабораторийн ажлаар JUnit 5 болон Mockito ашиглан нэгжийн тест бичих аргыг сурсан. Mock объект ашигласнаар `CourseRegistrationService` классыг өгөгдлийн сан болон имэйл серверээс тусгаарлан шалгах боломжтой болсон. `when().thenReturn()` ашиглан өөр өөр нөхцөл үүсгэж, `verify()` болон `never()` ашиглан методын дуудлагыг шалгасан. Мөн `ArgumentCaptor` ашиглан имэйлийн агуулгыг шалгаж, `doThrow()` ашиглан имэйл илгээх үеийн алдааг туршсан. Параметрчилсэн тестээр олон алдааны нөхцөлийг шалгаж, нийт 10 тестийг амжилттай ажиллуулсан. Mutation testing-ийн гурван туршилтаар тестүүд зориуд оруулсан алдааг илрүүлж чаддагийг баталгаажуулсан. Иймээс зөв зохиосон тест нь программын найдвартай байдлыг сайжруулж, цаашдын өөрчлөлтийн үед алдаа гарах эрсдэлийг бууруулахад тусалдаг.
